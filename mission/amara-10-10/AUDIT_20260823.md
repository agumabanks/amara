# Repository Audit — 2026-08-23

## Executive verdict

Amara has a thoughtful safety model and a credible phone-control prototype, but the repository is not yet a complete autonomous-employee system and was less mature than the machine-readable dashboard claimed. The strongest work is the bounded capability model, device-side receipts, human handoff policy, Flutter mission-control UI, and explicit separation between local code completion and Oppo evidence. The weakest areas were enforcement at the final side-effect boundary, privacy boundaries around prompts/logs, stale mission bookkeeping, and unverified breadth.

This audit corrected the high-confidence safety and consistency defects listed below. The remaining work is primarily architectural hardening and real-device certification; it should not be represented as finished based on compilation or unit tests.

## What is working well

- The Observe → Analyze → Act → Verify → Report loop is bounded by action and replan budgets.
- The model chooses from an allow-list instead of receiving raw Accessibility primitives.
- Read-only Soko skills distinguish account login, staff PIN, application state, and unsupported/protected screens.
- Durable tables exist for task journals, approvals, findings, schedules, selector outcomes, and side-effect receipts.
- Recurring occurrences are claimed before execution, preventing a process crash from blindly repeating the same occurrence.
- App switching verifies the foreground package, and visual claims require screenshot provenance.
- The owner can stop active work; scheduled work checks device activity and quiet hours.
- Local Android and Flutter test/build automation is consolidated in one gate script.

## Corrections made in this audit

### Critical safety and correctness

- Enforced exact Soko edit approval at execution time. Save now requires an unexpired approved record matching the listing, field, and value; the approval is consumed before save and the attempt receives an idempotency receipt.
- Changed external-side-effect retry classification to derive from the capability registry. TikTok posts and approved edits can no longer enter automatic recovery as though they were reversible reads.
- Restricted activity-injected test commands to debug builds, removed duplicate owner-chat recording, and consumes test extras so `onResume` cannot replay a command.
- One-time owner workers no longer retry after an exception, because an exception may occur after an externally visible action.
- TikTok publish intent is derived from the owner's command, not model-authored rationale; a request containing `draft` cannot be promoted to publish by the plan text.

### Policy, privacy, and configuration

- Removed hard-coded default owner phone and Terminal PIN values.
- Removed customer conversations, recent action text, and pending owner instructions from the global model-memory context. A conversation skill still supplies only the selected chat's scoped context.
- Removed sender, conversation, and message bodies from Android notification logs and removed generated reply text from success logs.
- Remote configuration can no longer overwrite locally entered Groq/Soko credentials.
- Groq requests now reject non-HTTPS endpoints.
- Removed the unused biometric permission.

### Consistency and maintainability

- Registered implemented Soko reporting and TikTok read capabilities that the controller already exposed, eliminating policy rejection of valid actions.
- A successfully created edit proposal now reports success rather than making the controller classify it as a failed action.
- Removed the deterministic Soko-edit shortcut that always emitted an empty, non-executable proposal; structured edit requests now go through bounded planning.
- Restored `agent_active` to false through a `finally` boundary on every controller exit.
- Reconciled `progress.json` with `taskboard.csv`, corrected status counts, and reverted device-only gates that had been promoted without evidence.
- Corrected documentation that described the operational SQLite database as encrypted.

## Remaining high-priority gaps

### P0 — must resolve before side-effect certification

1. **Prompt injection resistance:** screen text and inbound messages are untrusted data inside planning prompts. Add typed data envelopes, explicit instruction/data separation, adversarial fixtures, and a policy decision that is independent of model prose.
2. **Universal side-effect ledger:** chat attachments, media Status, inbound replies, follow-ups, legacy broadcast modules, and direct UI methods do not all use one shared claim → act → verify → finalize protocol.
3. **Verification strength:** several sends are verified by visible text or screen change, which can match drafts, quoted text, or stale content. Verification must bind package, exact target, normalized content hash, timestamp window, and delivery/publication state.
4. **Privacy/export governance:** backend logging can transmit summaries, metadata, stack traces, owner identity, and business context. Define an explicit opt-in telemetry policy, redaction layer, retention limits, deletion/export controls, and tests.
5. **Approval usability and atomicity:** approval and application are separate owner turns. Provide an explicit “approve and execute” workflow with a transaction state machine and a clear uncertain-result resolution path.

### P1 — required for dependable autonomy

1. The capability registry, planner prompt, executor `when`, recovery allow-list, UI descriptions, and tests are duplicated sources of truth. Replace them with one typed capability specification.
2. Operational memory has no retention policy, schema-level provenance for every fact, or encrypted database. Decide threat model and implement lifecycle controls.
3. Accessibility selectors and verifiers need versioned app adapters, screen contracts, confidence telemetry, and golden hierarchy regression fixtures.
4. Scheduling needs observable missed/deferred occurrence states, timezone-change handling, reboot evidence, and a clear distinction between exact time and Android's execution window.
5. Model calls rely on a single provider and network path. Add deadline budgets, offline-safe behavior, circuit breaking, and deterministic fallbacks per skill.
6. The current Soko architecture is mixed: the stated mission says screen-first/no new Soko API, while legacy backend/Soko API modules remain instantiated. Retire them or formally define their trust and activation boundaries.
7. The native C++ parser is a pass-through and its scheduler only computes `max(0, target-now)`. Either give native code a justified reliability role with tests or remove the extra build surface.

### P2 — engineering quality

1. Split `AccessibilityActions`, `AmaraMemory`, `AutonomyController`, `MainActivity`, and large Flutter screens into focused components.
2. Add database migration tests, controller integration tests with fake skills/model responses, MethodChannel contract tests, privacy/log tests, and release-manifest tests.
3. Resolve deprecated Android APIs used for service discovery, keyguard control, display sizing, and window flags.
4. Turn release shrinking on after keep-rule validation, and document key rotation/release provenance.
5. Reduce repository clutter by moving historical screenshots/XML into a dated evidence hierarchy with a generated index. Build outputs are ignored but currently consume most of the working directory.
6. Restore repository provenance. This workspace contains no `.git` directory, so the “recent refinements” could not be diffed against their predecessor or attributed commit-by-commit.
